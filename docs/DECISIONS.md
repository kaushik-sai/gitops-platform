# Decisions

Ambiguities and the call made, one line each.

## Phase 1: Foundation

| # | Question | Decision | Why |
|---|----------|----------|-----|
| 1 | Workload to deploy | Online Boutique v0.10.7. The release manifest is vendored unchanged in `apps/boutique/base/upstream/`, with its LICENSE and a README naming the source URL. Changes are made only in the kustomizations | A real multi-service app (12 Deployments: 10 services, a load generator, Redis). Not a fork and not a remote kustomize base: the version is pinned, an upgrade is a reviewable diff, rendering needs no network fetch, and the Apache-2.0 license stays with the code |
| 2 | Local cluster | kind v0.33.0, one control-plane node, node image `kindest/node:v1.37.0` pinned by digest, API server on 127.0.0.1 | Fits in about 7.6 GiB of Docker memory, with that memory left for the workloads. The digest makes every run use the same image. The same tool runs in CI |
| 3 | Environments | dev and prod as namespaces in one cluster (`boutique-dev`, `boutique-prod`), 1 replica per Deployment | Two clusters don't fit the laptop. A real setup uses separate clusters, and separate accounts or subscriptions (DESIGN.md) |
| 4 | How Argo CD finds the apps | App of apps. The root is a small Helm chart, `clusters/local`, that renders one Application per environment listed in its `values.yaml` | One value, `targetRevision`, reaches every child Application, so CI can deploy a PR's exact commit |
| 5 | Where the root Application comes from | `Start-Platform.ps1` builds it as data (`Build-RootApplication`) and applies it with kubectl. It is not a committed YAML file | The repository URL and revision are only known at run time (a branch on the laptop, the PR's commit in CI). Pester tests check its shape |
| 6 | Who installs and upgrades Argo CD | `Start-Platform.ps1`, with Helm: chart `argo-cd` 10.10.3 (Argo CD v3.5.5) from `oci://ghcr.io/argoproj/argo-helm/argo-cd`. Argo CD does not manage itself yet | Avoids two owners of one Helm release. Self-management comes in Phase 5 |
| 7 | Access to Argo CD | Anonymous read-only UI (`users.anonymous.enabled`, `policy.default: role:readonly`) over a port-forward on 127.0.0.1, with `server.insecure` (no TLS inside the cluster). The `admin` account stays for break-glass; its password is in the `argocd-initial-admin-secret` Secret | Changes go through Git, so nobody needs write access in the UI, and no password is committed. Same idea as sk-devops-svc decision 57 (Grafana anonymous viewer) |
| 8 | Dex and notifications | Disabled | No SSO or alerts yet, and it saves memory |
| 9 | `frontend-external` (a LoadBalancer Service) | Deleted by a patch in the base | kind has no load balancer, so the Service would stay Pending and Argo CD would report the app as Progressing forever. The frontend is reached with a port-forward |
| 10 | Load generator | Prod only: the dev overlay deletes its Deployment and ServiceAccount | Prod needs steady traffic for the canary analysis in Phase 4. Dev saves the memory (256 Mi requested) |
| 11 | Sync policy | Automated, with prune and self-heal; the environment Applications also have `CreateNamespace=true` | Git is the only way to change the cluster: manual changes are reverted, and what is removed from Git is removed from the cluster |
| 12 | Script language and test design | PowerShell 7 (cross-platform), with the same test design as sk-devops-svc: one CLI wrapper, `Invoke-Cli`, that Pester mocks | The scripts run on Windows locally and on Ubuntu in CI. Tests need no Docker or cluster |
| 13 | Which cluster the scripts act on | Every kubectl and helm call names the kind context, `kind-<cluster>` (`--context`, `--kube-context`) | The scripts never touch another cluster that happens to be the current context, such as docker-desktop or a work cluster |
| 14 | CI | GitHub Actions on GitHub-hosted runners, workflow `ci` with jobs `validate` and `e2e`. `e2e` builds the whole platform from scratch on every PR, from the PR's own commit (and on every push to `main`) | Free for public repositories and visible to anyone. A PR's `e2e` job passes only if the platform really comes up and both environments pass the smoke test |
| 15 | Tool versions | Pinned: kind v0.33.0, the node image by digest, Helm v4.3.0 (not v4.3.1, which was released the day this repo started), Argo CD chart 10.10.3; in CI also kubeconform 0.8.0, Pester 5.9.1, PSScriptAnalyzer 1.25.0. CI checks the kind, Helm and kubeconform downloads against their published SHA-256. kubectl in CI is the runner image's own | Every run uses the same tools, and a changed or tampered download fails instead of running |
| 16 | Smoke test | `Test-Smoke.ps1`, through a port-forward to the frontend: `/_healthz`, `/`, a product page and `/cart`, each expecting HTTP 200 and a known text | To render these pages the frontend calls the product catalog, currency, ad, recommendation, cart and shipping services, and Redis through the cart. Checkout, payment and email are called only when an order is placed, so they are not covered |
